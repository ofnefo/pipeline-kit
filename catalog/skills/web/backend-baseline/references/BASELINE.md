# Backend baseline: rules for the server side of web projects

Own text. Sources credited in `../NOTICE.md`; Postgres rule ids are cited as `pg:<file>` (supabase-postgres-best-practices).

Scope: any server side of a web project (Next.js route handlers/server actions, FastAPI, bots). Complements a general security
baseline (transport, headers, CSP, secret storage) and does not repeat it. Supabase RLS appears only as a reference for tenant
isolation. A project uses this as an acceptance gate: each item is **pass / fail / n.a.** with evidence (file:line, query output,
test, receipt); `CHECKLIST.md` is the template.

## 1. Postgres
1. **Every FK column has an index whose first column is that FK**, unless the table is tiny and never filtered by it (record the
   exception). Check with a catalog query, read-only, on a dev copy. (pg: schema-foreign-key-indexes)
2. **Hot filters have composite indexes in filter order** (equality columns first, then range/sort); partial indexes for
   "active only" lists. Prove with `EXPLAIN (ANALYZE, BUFFERS)` on a dev copy, not by guessing. (pg: query-composite-indexes,
   query-partial-indexes, monitor-explain-analyze)
3. **No N+1**: list pages load relations in one query (`include` / `IN (...)` / join), never per row in a loop. (pg: data-n-plus-one)
4. **Lists are paginated with a hard upper `take`**; keyset/cursor pagination for feeds and anything that can exceed a few
   thousand rows; `OFFSET` only for small admin tables. (pg: data-pagination)
5. **Short transactions**: no network calls (messengers, AI, object storage, e-mail) inside a DB transaction; `SELECT ... FOR
   UPDATE` only on the row that serialises the operation; consistent lock order. Queues use `FOR UPDATE SKIP LOCKED`.
   (pg: lock-short-transactions, lock-deadlock-prevention, lock-skip-locked)
6. **Constraints in the DB, not only in code**: `UNIQUE` for business keys (one registration per person+event, one scan per
   ticket), `CHECK` for ranges, `NOT NULL` by default. These make retries safe (§3). (pg: schema-constraints)
7. **Connections**: one pooled client per process; pool size x instances < `max_connections`; idle timeout set. (pg: conn-*)
8. **Raw SQL** only through parameterised tagged templates; `$queryRawUnsafe` or string concatenation is a fail unless the input
   is a constant.

## 2. Authorization (ASVS chapter: access control)
1. **Every handler authenticates first** (session or verified signature), then authorises **the object**, not only the role:
   load by `{ id, tenantId }` (or the project/event scope), or call an access helper before any `where: { id }` write.
2. **Tenant scope is applied in one helper**, not repeated ad hoc; tests include "user of tenant A asks for an id of tenant B
   -> 404/403".
3. **Unauthenticated API calls get 401/403 JSON**, not an HTML login redirect (clients and bots must not parse a login page).
4. **The role matrix lives in code and docs** (who can view/edit finance, participants, exports); bulk actions and exports check
   the same rules as single actions.
5. **Telegram Mini Apps**: identity only from server-side verification of `initData` (HMAC with the bot token);
   `initDataUnsafe` is never proof of identity.

## 3. Webhooks, jobs and repeated actions
1. **Verify before parsing**: shared secret/HMAC compared in constant time; reject with 401 and no body detail.
2. **Idempotency key per external event** (`update_id`, payment id, QR code) stored under a `UNIQUE` constraint; processing is
   `INSERT ... ON CONFLICT DO NOTHING` / upsert, so a repeated delivery is a no-op that still returns 2xx.
3. **Acknowledge fast, process durably**: store the event (state `PENDING`), answer 2xx, process in a job with retry and
   backoff; failed events stay visible with the error (a history a manager can read, §6).
4. **Malformed payloads**: return 2xx only if the provider would otherwise retry forever, and log them at `warn` with the event id.
5. **User double actions**: double click, repeated form submit or repeated QR scan produce one effect (disabled submit + server
   idempotency key or unique constraint; the second attempt returns the first result).
6. **Limits** (seats, points, quotas) are enforced in one transaction with a lock or a conditional update
   (`UPDATE ... WHERE remaining > 0`), never "read, check in JS, write".

## 4. Migrations
1. Forward migrations are generated by the project tool (Prisma, Alembic, ...) and reviewed as SQL.
2. **Expand -> migrate -> contract** for anything that drops/renames a column or tightens a constraint on a live table: add new,
   backfill, switch code, remove the old part in a later release.
3. **Each migration states its rollback** (down SQL, or "forward-fix only" + why) and whether it locks a large table
   (`CREATE INDEX CONCURRENTLY` for big tables, in a separate non-transactional migration).
4. **Never run `migrate dev` / `reset` / `db push` against production**; production gets `migrate deploy` only on the operator's
   explicit request for that site, after a verified backup.
5. Development uses a copy (`CREATE DATABASE ... TEMPLATE ...`), never the shared dev DB for destructive experiments.

## 5. Structured logs and request id
1. **One logger** (JSON lines: `ts, level, msg, requestId, userId?, tenantId?, route, durationMs, err`), not scattered `console.*`.
2. **Request id**: accept `x-request-id` from the proxy or generate one in middleware; return it in the response header and put
   it into every log line and into user-facing error messages ("error code: ...") so a manager can report it.
3. **Never log** secrets, tokens, passwords, full card/passport data, raw `initData`; mask phone/e-mail when not needed.
4. Webhook/job logs carry the external event id; AI calls log model, tokens and cost (§7).
5. A health endpoint checks the DB (`SELECT 1`), is public, and returns no internals.

## 6. API contracts and failure paths
1. Inputs validated by schema (zod/pydantic) at the boundary; errors return a stable shape `{ error: { code, message } }` with a
   `message` in the UI language.
2. Every endpoint group has a contract smoke: happy path, unauthenticated, wrong tenant, invalid body, repeated call.
3. Timeouts on every outbound call; an external outage degrades the feature, not the page.
4. **Field work** (venues, weak networks): forms keep entered data on network loss, submit is retryable with the same idempotency
   key, the UI says whether the last attempt reached the server.
5. **Manager output**: search, bulk actions, CSV/XLSX export (UTF-8 with BOM for Excel, `;` separator for locales with a decimal
   comma, or real XLSX), and an error-history screen for webhooks/jobs/imports.

## 7. Event context and AI features
1. Time zone is explicit: stored per event/venue, all timestamps `timestamptz`, displayed in the event's zone.
2. Team roles and the service lifetime (when registration opens/closes, when data is archived) are configuration, not code.
3. Long names (full names, multi-part surnames) fit without losing meaning; error messages are written for humans.
4. AI calls: per-request cost recorded, per-tenant/day limit, timeout, behaviour when the model is unavailable, and a manual
   "stop the task" control. Prefer local models; paid cloud only when the operator asked for it for that job.

## 8. Secrets
Covered by the security baseline; minimum here: secrets only in the executing user's environment or an untracked `.env.local`,
never in Git, API collections, logs, project notes or command arguments. Collections reference environment variables only.
