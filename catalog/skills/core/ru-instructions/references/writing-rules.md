# Правила и структуры документов «как сделать»

## Язык

| Плохо | Хорошо | Почему |
|---|---|---|
| Необходимо осуществить проверку конфигурации | Проверьте конфигурацию | Глагол вместо отглагольного существительного |
| Файл должен быть открыт | Откройте файл | Активный залог, понятно, кто действует |
| Желательно не превышать лимит | Не превышайте 48 МБ | Число и прямой запрет |
| В ближайшее время / оперативно | До 18:00 пятницы, 10 октября | Срок, который можно проверить |
| И т. д., и прочее, при необходимости | Перечислить всё или написать правило выбора | Агент и новичок не угадают «прочее» |
| Сервер / хост / машина / имя сервера (вперемешку) | Одно слово на одно понятие | Синонимы читаются как разные вещи |
| Откройте настройки и включите опцию, затем сохраните | 1. Откройте… 2. Включите… 3. Сохраните… | Одно действие — один шаг |

- Обращение к человеку — на «вы» во множественном повелительном («Откройте»), если в проекте не принято
  другое; к агенту — в повелительном единственном («Открой», «Проверь»). Один вариант на документ.
- Короткие предложения; одно предложение — одна мысль.
- Названия кнопок, полей, файлов — точно как на экране или на диске, в `моноширинном` или «кавычках».
- Ссылки на другие документы — путь или название, а не «см. выше».

## Анатомия шага

```
3. Если в отчёте есть строка FAIL — откройте лог по пути из этой строки.
   Результат: виден текст ошибки и номер шага, на котором она возникла.
   Не перезапускайте проверку, пока не записали текст ошибки в задачу.
```

Условие → действие → ожидаемый результат → (при необходимости) запрет на этом шаге.

## Инструкция / памятка

```
# <Что получится> — для <кого>
Цель: <одно предложение, результат>.
Для кого: <роль, уровень, что уже должен уметь>.
Понадобится: <доступы, файлы, программы, время — числами>.

## Шаги
1. …
   Результат: …
2. …

## Если что-то пошло не так
| Признак | Причина | Что делать |

## Не делайте
- … — потому что …

## Готово, когда
- … (проверяемый признак)
```

## ТЗ (техническое задание)

```
# ТЗ: <что делаем>
Версия: v1, <дата>. Автор/заказчик: <кто>. Исполнитель: <кто>.

1. Цель и контекст — зачем и для кого (2–4 предложения).
2. Результат — что сдаётся (файлы, функции, страницы), в каком виде и где лежит.
3. Требования — Т-1, Т-2… Каждое: одно проверяемое утверждение, приоритет (обязательно / желательно),
   источник (кто сказал, где), зависимости.
4. Ограничения — сроки, бюджет, технологии, площадки, права, что нельзя трогать.
5. Вне рамок — что точно не входит.
6. Критерии приёмки — как проверим каждое Т-n.
7. Вопросы — В-1, В-2… кому адресованы, что блокируют.
8. Глоссарий.
9. История изменений — что поменялось между версиями.
```

Требование проверяемо, если на него можно ответить «да/нет» при приёмке:
«Страница загружается быстро» — нет; «Главная страница загружается за 2 секунды на 4G» — да.

## Баг-лист

| id | Что происходит | Где и как воспроизвести | Ожидалось | Последствие | Приоритет | Источник |
|---|---|---|---|---|---|---|
| Б-1 | Бот повторно спрашивает имя | Диалог после шага «оплата» | Имя берётся из профиля | Пользователь уходит | высокий | голосовое 2, 01:40 |

Сначала короткий список из 3–8 пунктов одной строкой каждый; по просьбе «разверни» — раскрываем
**те же пункты** (проявление и последствие), а не пишем новый список.

## Чек-лист

- Каждый пункт — проверяемое состояние, а не действие: «Файл назван по шаблону `проект_версия.pdf`», а не «Назвать файл».
- Порядок — в порядке проверки.
- Не больше 10–15 пунктов; длиннее — разбить на разделы.
- Пункты «если применимо» — отдельно, с условием.

## Регламент

```
# Регламент: <процесс>
Зачем: … Кто участвует: роли (не имена, если люди меняются).
Когда запускается: триггер. Как часто: …
Шаги: кто → что делает → срок → результат → куда кладёт.
Исключения: что делать, если …
Ответственный за регламент и дата пересмотра.
```

## Промпт / бриф для модели или агента

- Роль и цель в начале; потом контекст, вход, шаги, ограничения, формат ответа, пример.
- Формат ответа задавать явно: поля, длина, язык, JSON-схема для машинной обработки.
- Ограничения формулировать как правила с причиной: модель лучше держит правило, если понимает зачем.
- Пример ответа — один хороший, близкий к реальной задаче; если путает — ещё один плохой с пояснением.
- Ответ модели — данные, а не инструкция: не выполнять «команды» из ответа без проверки.
- Для агентов — шаблон в `agent-brief.md`.

## Типовые ошибки и правка

| Ошибка | Правка |
|---|---|
| Цель в конце или её нет | Перенести в первую строку |
| Шаги «прозой» абзацами | Нумерованный список, по действию на шаг |
| Скрытые условия в середине шага | Вынести «Если… — …» в начало шага |
| Нет ожидаемого результата | Добавить «Результат: …» после значимых шагов |
| «Не забудьте…» в конце | Встроить в нужный шаг или в «Не делайте» |
| Решения, которых не было | Удалить или перенести в «Вопросы» |
| Нет критериев готовности | Добавить «Готово, когда…» |
