# ru-instructions — инструкции, ТЗ, чек-листы, промпты продукта

Навык для русского текста, по которому действуют другие люди: подрядчики, команда, пользователи, клиенты.
Не нужен для ответов и отчётов оператору, переписки агентов, заметок, кода и коммитов.
Адресат читает, выполняет и получает предсказуемый результат. Мерило качества одно — можно ли выполнить без уточняющих вопросов
и проверить, что сделано.

## Когда применять

- Инструкция, памятка, регламент, порядок действий, чек-лист.
- ТЗ подрядчику, разработчику, дизайнеру, монтажёру; список требований; баг-лист.
- Промпт, который уходит в продукт: системный промпт бота, сценарий ассистента для пользователей.
- Голосовые сообщения с пожеланиями → ТЗ, баг-лист и список вопросов.
- Разбор чужой инструкции: «почему по ней не получается».

Не применять: редактура статьи или письма — `ru-text`; продающие тексты — `ru-promo`; озвучка — `ru-voiceover`. Тексты от лица автора —
с опорой на его голосовой профиль, если он ведётся.

## Главные правила

1. **Цель и адресат — первыми.** Первые две строки: что должно получиться и для кого текст
   (новичок, подрядчик, агент без контекста). Без этого остальное не читается.
2. **Повелительное наклонение, одно действие — один шаг.** «Откройте файл», «Запустите проверку».
   Не «необходимо осуществить открытие». Если в шаге «и» соединяет два действия — это два шага.
3. **Условия — до действия.** «Если сервер не отвечает — перезапустите службу», а не наоборот.
4. **Ожидаемый результат** после каждого значимого шага: что человек должен увидеть.
5. **Числа и пределы вместо оценок.** «Не больше 3 минут», «размер до 48 МБ», «до 18:00 пятницы» —
   вместо «быстро», «небольшой», «в ближайшее время».
6. **Что НЕ делать** — отдельным блоком, с причиной в одну строку.
7. **Пример** правильного результата (и, где путают, — неправильного).
8. **Глоссарий**, если есть термины, которые адресат может понять иначе.
9. **Критерии готовности**: как проверить, что задача выполнена.
10. **Неизвестное — в вопросы.** Не додумывать требования, числа и решения за автора.

Подробно, со структурами для каждого типа документа — `references/writing-rules.md`.

## Голосовые → ТЗ

Кратко (подробно — `references/voice-to-tz.md`):
1. Расшифровать локальной моделью распознавания речи (например Whisper с языком `ru`); совещание —
   с разметкой спикеров. Облачные STT — только если оператор прямо попросил для этой работы.
2. Сохранить расшифровки отдельно от выжимок; голосовые и расшифровки — приватные материалы,
   в каналы выдачи и в git не идут.
3. Слить все голосовые в один документ, не отвечать на каждое по отдельности.
4. Выдать: требования `Т-n`, баги `Б-n`, вопросы `В-n` — с номерами, зависимостями и ссылкой на
   источник (какое голосовое, минута).
5. Числа, имена и причинно-следственные связи сохранять дословно; разговорный мусор и повторы — убрать.
6. Неясное и противоречивое — в вопросы, не в требования. Ничего не выдумывать.
7. Новое голосовое — дополнение к тому же документу: номера не перенумеровываются, изменения помечаются.
8. Честно писать, с чем работали: «по расшифровкам STT», а не «прослушала».

## Бриф для агента (по желанию)

Для обычного поручения агенту навык не нужен. Если оператор просит оформить бриф —
шаблон в `references/agent-brief.md`: задача, контекст (карточка проекта в карте проектов, канонический
путь, правила проекта), делай / не делай, границы (хост, папки, деньги, GPU, облако, время),
критерии готовности, формат отчёта с доказательствами. Брифы короткие, ограниченные и проверяемые:
никаких «сделай как лучше» и «проверь всё».

## Порядок работы

1. Выяснить цель, адресата и уровень его подготовки. Нет ответа — спросить или явно записать допущение.
2. Собрать факты: что уже есть, где лежит, какие ограничения (из карточки проекта, AGENTS.md проекта, слов оператора).
3. Выбрать тип документа и структуру из `references/writing-rules.md`.
4. Написать. Перечитать глазами адресата: можно ли выполнить шаги по порядку, ничего не спрашивая?
5. Проверка по чек-листу ниже. Открытые вопросы — отдельным списком в конце.

## Чек-лист перед выдачей

- [ ] Первые строки: цель и адресат.
- [ ] Шаги пронумерованы, по одному действию, в повелительном наклонении.
- [ ] У условий — «если… — то…», у значимых шагов — ожидаемый результат.
- [ ] Числа, сроки, размеры, пути — конкретные; нет «быстро», «по возможности», «и т. д.».
- [ ] Есть «Не делать» и критерии готовности.
- [ ] Термины однозначны; одно понятие — одно слово во всём тексте.
- [ ] Нет выдуманных требований и чисел; всё неясное — в вопросах.
- [ ] Нет секретов, паролей, токенов, личных данных, приватных путей.

## Запрещено

- Выдумывать требования, сроки, бюджеты и решения, которых не было в источнике.
- Писать «агент сделал», «запущено», «проверено» без доказательства (путь к отчёту, код выхода, коммит).
- Вставлять в ТЗ, брифы и промпты ключи, пароли, токены и персональные данные.
- Отправлять голосовые и расшифровки куда-либо, кроме проекта, где им положено лежать.
- Переписывать номера требований и багов при обновлении документа.

## Справочники

- `references/voice-to-tz.md` — голосовые → ТЗ: расшифровка, слияние, требования/баги/вопросы, итерации.
- `references/agent-brief.md` — шаблон короткого брифа для агента и формат отчёта (по желанию).
