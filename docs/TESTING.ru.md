# Проверки и приёмка

Для агента и владельца новой установки. Цель — показать, какие сценарии работают в этой среде, и сохранить достаточно данных для повторения проверки.

## Правила результата

Используйте статусы `pass`, `fail`, `blocked`, `not_run`, `not_selected`. Для каждого выбранного сценария укажите критерий до запуска, фактический результат, команду/действие, код выхода при наличии и путь к доказательству. Шаблон — [acceptance-receipt.example.json](../config/acceptance-receipt.example.json).

`pass` требует доказательства; отсутствие ошибки в логе недостаточно, если не проверен ожидаемый файл или поведение. Пропуск необязательной зависимости не является PASS. Отдельно записывайте техническую проверку, независимое ревью и решение владельца о качестве.

## 1. Чистая установка и автоматические тесты

Сначала зафиксируйте выбор по [AUTO-SETUP](AUTO-SETUP.ru.md). Для частичной установки проверяйте выбранные маршруты; отсутствие невыбранного инструмента — `not_selected`. Приведённый ниже полный прогон подходит для выпуска Kit или установки со всеми зависимостями тестов. Установщик скиллов отдельно проверяется командой `python -m unittest discover -s tests -p test_setup_skills.py -v` без дополнительных библиотек.

В новом каталоге программы создайте новое Python 3.12 окружение. Не подключайте библиотеки из прежней установки. Команды выполняйте из корня Kit Python-интерпретатором этого окружения:

```text
python -m pip install -r requirements-test.txt
python -m pip install -r requirements-office.txt
python -m pip check
python -m pip freeze
python -m unittest discover -s tests -v
python pipeline_kit.py --workspace ../pipeline-test-workspace init
python pipeline_kit.py --workspace ../pipeline-test-workspace doctor
```

Вторая установка нужна для полного имеющегося набора проверок Office. Зафиксируйте ОС, Python, версию Kit, зависимости, stdout/stderr и код выхода. Исходная опубликованная сборка прошла 27 тестов; при обновлениях сверяйте фактическое число и причины пропусков, не требуйте старое число искусственно.

| Файл | Что он проверяет |
| --- | --- |
| `tests/test_control.py` | Локальную панель/API, проекты, файловые операции, задачи, NameNode и границы доступа |
| `tests/test_local_chat.py` | Протокол на подставных ответах, opt-in, поток и запрет неподходящих endpoint |
| `tests/test_modules.py` | Выбранные производственные команды и контрольные результаты |
| `tests/test_release.py` | Правила состава выпуска и проверки упаковки |

Тест локального чата не запускает реальную модель. `doctor` показывает наличие инструментов; он не доказывает качество генерации или корректность всего производственного маршрута.

## 2. Практический путь в панели

Запустите панель с отдельным тестовым workspace и свободным портом, например: `python pipeline_kit.py --workspace ../pipeline-test-workspace serve --port 8771`. Откройте `http://127.0.0.1:8771`; убедитесь, что работает именно тестовый экземпляр. Если порт занят, выберите другой и измените адрес во всех командах проверки. На ширинах 1440 и 375 пройдите сценарий:

1. Создайте проект и найдите его после перезагрузки страницы.
2. Загрузите маленький тестовый файл, откройте его, измените текст и снова прочитайте.
3. Переместите тестовый файл в карантин и восстановите; сравните содержимое.
4. Создайте задачу, запустите её через CLI, отправьте результат на проверку и примите в панели.
5. Повторите изменение со старой версией задачи: оно должно быть отклонено без потери нового состояния.
6. Откройте Studio, создайте чат и проверьте сохранение. Генерацию проверяйте только после подключения реального сервера.
7. Выполните экспорт выбранного модуля и откройте полученный файл.

Сохраните скриншоты ключевых состояний и ошибки консоли. Автоматический браузерный проход: `python tools/browser_check.py --base-url http://127.0.0.1:8771 --output <evidence-directory>`; Playwright и браузер устанавливаются отдельно в тестовом окружении. Утилита не заменяет все ручные шаги выше. Не запускайте проверку на рабочем workspace: она создаёт данные. Ссылки отдельных инструментов могут использовать стандартный порт 8770; проверяйте адрес и не переходите из тестового экземпляра в рабочий.

## 3. NameNode и агент

Выполните пример из [NAMENODE.ru.md](NAMENODE.ru.md). Убедитесь, что вторая сессия получает отказ при чужом claim, сообщение появляется в inbox адресата, журнал содержит результат, а release снимает владение.

В новой сессии агента проверьте: прочитаны нужные правила; выбран применимый скилл; используются правильные каталоги; задача выполняется только после claim; отчёт содержит реальные пути и результаты. Для скилла проверки графики дайте маленький файл, выполните анализ и сравните вывод с исходником. Обнаружение скилла и успешное выполнение его сценария — разные проверки.

## 4. Производственные примеры

| Маршрут | Контрольный материал | Что считать успехом |
| --- | --- | --- |
| Графика | `examples/composition.json` | Выход 640×360, отдельный proof, просмотр слоёв/текста; исходник не изменён |
| Печать | Явные размеры, PPI и поля из тестового задания | Проверенные расчёты и правильное отклонение неподходящего файла |
| Office | `examples/estimate.json` | Стоимость 600.00 и прибыль 198.00 при ставках примера; не универсальные ставки |
| Видео | Короткий синтетический ролик | ffprobe подтверждает заданные размер, fps, длительность и кодек; просмотр без обрывов |
| Звук | Короткий собственный тестовый сигнал | Отчёт громкости/пиков в заданных пределах, сохранённая длительность и прослушивание |
| Web | Сохранённый HTML с известным дефектом | Дефект найден, после исправления результат меняется ожидаемо |

Используйте команды из [MODULES.md](MODULES.md), задайте ожидаемые значения до запуска. Храните вход и результат отдельно; для проверки неизменности сравнивайте хеши исходников до и после. Проверка видеоэкспорта FFmpeg не проверяет нейросетевую видеомодель.

## 5. Реальные модели

Для выбранной модели соберите небольшой набор реальных для задачи примеров: обычный, граничный, некорректный вход и ранее известная ошибка. До прогона задайте критерии и допустимое время. Сохраните исходные входы, параметры, полный результат, версию профиля и замеры.

Выполните успешный запрос через фактический клиент, затем проверьте недоступность сервера и некорректный model ID. Для потокового чата проверьте завершение и сохранение ответа. Для генерации файлов проверьте сам файл и его содержимое. Не записывайте заранее `pass` в шаблон отчёта.

При сравнении моделей используйте один набор входов и одинаковую рубрику. Для стохастической генерации заранее назначьте несколько повторов, сохраните seed, если движок его поддерживает, и учитывайте все результаты. Один удачный кадр не доказывает стабильность модели. Автоматические метрики дополняйте просмотром/прослушиванием и оценкой владельца.

## 6. Восстановление и обновление

На остановленном тестовом экземпляре сделайте копию workspace, восстановите в другой каталог и запустите панель с ним. Проверьте наличие файлов, карточек, задач и чатов. Зафиксируйте, какие данные покрывает копия: внешние модели, ассеты и исходники за пределами workspace требуют отдельной политики.

Для выпуска Kit используйте [RELEASE.md](RELEASE.md): явный список файлов, проверка пакета, перенос в новый каталог и независимое ревью. Для изменения только документации достаточно проверить ссылки, примеры и состав архива; не повторяйте GPU-прогоны и весь интерфейс без изменения соответствующего поведения.

## Когда установка готова

Основа готова, когда пройдены чистая установка, основной пользовательский путь, NameNode, правила агента и проверка восстановления. Каждый выбранный дополнительный модуль принимается своим примером. Если основа работает, а видеогенерация ещё не настроена, отчёт должен говорить именно это.

В итоговом сообщении перечислите рабочие сценарии, пути запуска и данных, проверенные модели/скиллы, ограничения и ссылку на локальный отчёт. Не называйте среду полностью готовой, если обязательный для владельца сценарий остаётся `blocked` или `not_run`.
